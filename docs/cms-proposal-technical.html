Overview

Architecture

SovereignTrust runs on Vercel (frontend + serverless API) with OASIS as the data and identity layer. The CMS will extend this existing pattern — no new infrastructure, no new vendors. Content is stored as OASIS holons in MongoDB (the same store the trust documents use), managed through new serverless functions that follow the same auth and error-handling conventions as the existing trust-save.js and trust-load.js endpoints.

The admin UI will be a new section of the existing trust site — same Next.js codebase, gated behind the existing JWT-based auth middleware.

Key dependency: All three options rely on the OASIS holon fix currently on the Fixing-Stateless-Holon-Update branch. Content holons use the same IsNewHolon / Id contract as trust document holons — this branch must be merged before CMS work goes to production.

Data model

Content as holons

Each piece of manageable content is an OASIS holon stored in MongoDB. The HolonType enum identifies what kind of content it is; the MetaData dictionary holds the actual content fields. This avoids any schema changes — the existing MongoDB collection and OASIS API handle everything.

Content holon types

HolonType Scope Key MetaData fields
CMSPage A slug, title, body, seoDescription
CMSFaq A question, answer, order, category
PricingPlan A name, description, price, features (JSON array)
TrustTemplate C templateName, fields (JSON array of field defs), pdfLayout

Example: a FAQ holon

{
  "HolonType": "CMSFaq",
  "Name": "What is a bare trust?",
  "MetaData": {
    "question": "What is a bare trust?",
    "answer":   "A bare trust is the simplest form of trust...",
    "order":    1,
    "category": "basics"
  }
}

Example: a trust template field definition

{
  "HolonType": "TrustTemplate",
  "Name": "Bare Trust",
  "MetaData": {
    "templateName": "Bare Trust",
    "fields": [
      { "id": "settlor_name",   "label": "Settlor full name", "type": "text",  "required": true  },
      { "id": "trust_value",    "label": "Trust value (£)",   "type": "number","required": true  },
      { "id": "special_notes",  "label": "Special conditions","type": "textarea","required": false }
    ],
    "pdfLayout": "bare-trust-v1"
  }
}

Option A

Content CMS

The simplest module. An admin screen lists all CMSPage, CMSFaq, and PricingPlan holons. Clicking any item opens a form editor. Saving calls the POST /api/cms-save endpoint (see API endpoints), which upserts the holon via OASIS. The frontend pages that display this content (education, FAQ, pricing) fetch their data from GET /api/cms-load at build time or on demand — whichever fits the Vercel cache strategy for the page.

Admin UI — editor screen

Minimal: a list view (name + last-edited date) and a form view. The form fields are generated from the holon type — CMSPage shows title + body textarea + SEO description, CMSFaq shows question + answer + order, and so on. No rich text editor is needed in the first release — plain textarea is sufficient for the expected content volume.

Frontend integration

Each public-facing page currently has its content hardcoded. After Option A these pages will call GET /api/cms-load?type=CMSPage&slug=education (or the relevant type + identifier) and render the returned content. A build-time fetch with a short stale-while-revalidate window (e.g. 60 seconds) is the recommended approach — content changes go live without a redeploy.

Option B

Admin Dashboard

A read/manage view of all holons in the system — primarily trust documents and user accounts. The dashboard calls the existing trust-load.js endpoint with an admin-scoped JWT (no new data access is needed; the admin role is already modelled in OASIS). Results are displayed in a searchable, filterable table.

What the dashboard shows

View Data source Actions
All trusts OASIS holons, HolonType.Trust View, download PDF, change status
All users OASIS avatars View profile, disable account
Support queue Holons flagged for review Mark resolved, add admin notes

New endpoint required

A single new endpoint: GET /api/admin-list — returns paginated holons filtered by type and optional search query, authorised by admin-role JWT. The existing load endpoint returns one holon by ID; the admin endpoint needs to return lists with server-side pagination.

Option C

Trust Template Builder

The largest module. A drag-and-drop form builder that writes TrustTemplate holons. Each template defines the fields shown in the trust creation wizard and the layout of the generated PDF.

Field type support (v1)

text, textarea, number, date, select (dropdown with configurable options), checkbox. Each field has: label, placeholder, required flag, validation rules (min/max length, regex pattern), and a PDF label (which can differ from the form label).

PDF generation

The existing trust PDF generation code reads from a fixed schema. After Option C this needs to be made template-aware — it should read the field definitions from the TrustTemplate holon and render them in the order and layout specified by pdfLayout. The pdfLayout value in v1 can be a named layout key (e.g. "bare-trust-v1") that maps to a predefined PDF template; a fully dynamic layout builder is a potential v2 feature.

Trust creation wizard

The existing trust creation form is currently driven by hardcoded field lists. After Option C it will fetch the TrustTemplate holon for the selected trust type and render the fields dynamically. This is the largest integration point: the wizard UI, the save logic, and the validation all need to work from the template definition rather than static code.

New endpoints

API endpoints

All endpoints follow the existing Vercel serverless function pattern. Auth is handled by the same JWT middleware used in trust-save.js. All requests and responses are JSON. OASIS errors are mapped to HTTP status codes consistently with the existing API.

  • GET /api/cms-load Returns one or more CMS content holons. Query params: type (required, e.g. CMSPage), slug or id (optional — omit to return all of that type). Public endpoint, no auth required.
  • POST /api/cms-save Creates or updates a CMS content holon. Body: { holonType, name, metaData } — plus id and IsNewHolon: false when updating an existing record. Admin JWT required. Follows the same IsNewHolon contract as trust-save.js — new holons omit id; updates include id and IsNewHolon: false.
  • GET /api/admin-list Returns a paginated list of holons by type. Query params: type, page, pageSize, q (search). Admin JWT required. Option B only.
  • GET /api/template-load Returns the TrustTemplate holon for a given trust type. Used by the trust creation wizard to build its form dynamically. Query params: templateName. Public endpoint. Option C only.
  • POST /api/template-save Creates or updates a TrustTemplate holon. Same body shape as cms-save. Admin JWT required. Option C only.

Auth and permissions

Auth model

The existing auth model (OASIS avatars, JWT issued on login, verified by middleware in each API function) is unchanged. The CMS adds one new role check: admin-gated endpoints verify that the avatarId in the JWT has the GlobalAdmin or PlatformAdmin role in OASIS. No new auth infrastructure is needed.

Role mapping

RoleCan access
Any authenticated user Their own trust documents, their own account
GlobalAdmin / PlatformAdmin All CMS save endpoints, admin-list, template-save, all trust documents
Anonymous cms-load (public content), template-load (public templates)

Deployment

Deployment notes

Prerequisites

Before any CMS code is deployed to production: the Fixing-Stateless-Holon-Update branch must be tested and merged. All CMS holons use the same OASIS save path as trust documents — a broken holon insert would silently discard content.

MongoDB

No schema changes required. CMS content holons land in the same Holon collection as trust documents, distinguished by HolonType. The first time a CMS holon is saved, OASIS creates it automatically. No migration scripts needed.

Vercel environment

The new API functions follow the same pattern as existing ones: no new environment variables, no new Vercel projects. Deploy alongside the existing functions. Option B's admin-list endpoint may need an index on HolonType + CreatedDate in MongoDB for acceptable query performance at scale — worth adding before launch.

Rollout order

Recommended: Option A → Option B → Option C. Each option is independently deployable. Option A delivers the highest immediate value (content autonomy) in the shortest time. Option B adds admin visibility. Option C is a separate phase and should not block A or B.
